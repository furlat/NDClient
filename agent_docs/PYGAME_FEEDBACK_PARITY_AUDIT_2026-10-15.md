# Pygame feedback and lifecycle parity audit — 2026-10-15

Read-only audit against Godot checkpoint `813d21f` (HEAD verified). No production files changed; no Godot, game, profiling or test process launched. This report covers non-Factory body/condition feedback and lifecycle. Locomotion/flight and Factory spell artwork/particle design are excluded. Source inspection establishes implementation, not rendered or audible qualification in the user's live game.

Evidence notation: `E` = `/mnt/c/Users/tommaso/Documents/Dev/dnd_engine/game_obsolete`; `G` = `/mnt/c/Users/tommaso/Documents/Dev/NDClientGodot`. Every `file:line` below is relative to that explicit root. Tests are existing reproductions inspected, not tests run in this audit. **Implemented** means a production compile/sample/render path exists; **partial** means an identified part of the original behavior is absent; **missing** means an authored original behavior has no corresponding production consumer; **unverified** means source evidence does not establish parity. These are not artistic approval claims.

## Findings

Basic visibility admission, condition colours/opacity, resting poses, outlines, semantic marker selection, positive-damage reactions, numbers, life-state bodies and badges are present. This is not an empty condition renderer. The substantial gaps are captured petrification pose and three legacy body-ramp mappings; state-driven equipment materials; Blur/Enlarge/Mirror Image/absence body handling; condition sequence/mask/loop clocks and response/activation channels; summon body lifecycle; slot-owned concentration area retention; and disintegration dust. Most have imported authoring already. Merely adding an icon or a Factory spell source cannot supply these behaviors.

Godot's own requirement inventory corroborates several gaps, but the classifications below also inspect the consumers. Its inventory is not sufficient evidence by itself: for example it marks `frozenPose` implemented while `captureCurrent` is not consumed, and its generic missing-feedback declarations must be reconciled with actual `Components.compile` output.

## Authoring, renderer and UI distinction

The condition catalog has 160 recipes, but a recipe is not a claim that every D&D condition needs every field. For example generic Stunned has head layers and no freeze, Hidden has feedback and no persistent tint, and disabled application/removal feedback is an explicit authoring choice. Existing condition Resources can overlay body filters/outlines/activity poses: `G/source_catalog.gd:25` calls `NativeAuthoring.overlay`, `G/presentation/native_authoring.gd:61` preserves legacy recipe then overlays selected fields. This audit checked that these overlays do not supply the missing bodyScale/bodyDistortion/liveCopies/absenceEcho, captured-pose or ramp mapping consumers.

Most findings F10–F17/F21/F22/F25/F26/F28 have authoring or retained old data and need executable ownership/sampling/render behavior, not additional artwork. F14 also needs the original semantic item-material recipe export assessed: imported base item variants/static tint are insufficient. Native replacements must be checked against `replaces_media` before restoring any original strip; drawing both would be a regression.

The client already exposes missing mechanisms in `event_trace.gd` and condition coverage, and draws floating text. Therefore these are primarily presentation gaps, not evidence of an absent UI. Catalog-wide availability is explicitly separate from rendered execution (`G/presentation/condition_coverage.gd:285`). Some inventory summaries can overstate implementation (captured frozenPose) or declare generic expectations before matching compiled components; use the actual occurrence/component/render witness. No UI implementation is prescribed here.

## Recommended finite follow-up qualification

Choose actual existing recorded cases for the gaps above; compare ordinary client and Studio through the same compiler/render pipeline, with before/onset/contact/clear/after seeks and one replay loop. Prioritize captured stone/ramp, invisibility alpha, overlapping rest-pose removal, held/floor item material, summon retirement, and disintegration, because they distinguish a correct final state from missing original intermediate presentation. Then check condition sequence/mask/response ownership and concentration slots. These are audit reproduction suggestions, not approval to implement or expand the migration plan.

No test execution or live-game observations support a claim of pixel/audio completion in this report. No performance changes, speculative requirements, particle redesign, or production edits were made.
