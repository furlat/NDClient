## Boundaries: actual old behavior versus intended features

1. **No demonstrated idle hover/bob system.** The inspected Pygame flight implementation is ground-to-ground finite travel with a smooth airborne plateau. At completion its tests require zero lift and settled support. `hover` search hits mainly refer to mouse input, and no body bob oscillator was found in the executable motion/forced samplers. Classify idle hover/bob **unverified/not established in the old implementation**, not a confirmed missing Godot feature. Art frames or a hovering creature pose are distinct from time-varying vertical body bob. Do not invent a perpetual air occupancy mechanic from the user's wording.
2. **Drag is not a separately established animation family.** The authoritative ForcedMovementFact (E facts.py:272) carries target/source, endpoint geometry, disclosed path, heights, drop and landing kind; it has no drag-specific pose/curve field. Old generic grounded displacement can serve a pulling/drag cause, but no separate drag body behavior was established. Likewise throw-like controlled/impact transfer is established by M6; a dedicated physical throw/ballistic fall system is not established by these files. Reproduction must use an actually supported SDK action, not manufacture a drag/throw command.
3. **Forced travel must not fabricate reactions.** Old native fixtures expressly assert no StepMovementEvent or AttackEvent in shove lineages (E game_obsolete/tests/game/test_forced_movement_history.py:43). A nearby watcher does not justify invented opportunity attacks. Factual hazard/damage descendants still own their real effects.
4. **Disabled or rejected authoring is not an active regression.** Old forced binder explicitly rejects media/recovery.media when nonempty (E forced_movement.py:125). Current forced recovery and movement recovery authoring can be disabled. This audit does not turn these declarations into claims of implemented old rendering. Missing default brace/release, flight and reached-cell scheduling are supported by executable old tests independently.
5. **Existing gap reporting is useful but not acceptance.** G presentation/requirements.gd:170 inventories flight_phases, connector_registration and reaction_lead_in. Its `row` documentation (`:2`, `:51`) explicitly does not certify rendering. Similarly component_trace checks that a forced track has `motion=true`, G tests/component_trace_checks.gd:124, but that does not qualify anticipation, path arrivals, flight lift or rig brace selection.

## Reproduction and validation limits

This audit traced finite executable paths and inspected tests/authoring; it did not execute old or new suites, change fixtures, create server encounters or capture the currently running Godot client. Source-backed missing behavior is reported as such, while displayed native outcomes remain unqualified where noted. Existing jump/window/OA recordings support inspecting implemented paths without new backend work; matching Fly/Telekinesis/shove hazard recordings may require a later explicitly authorized gameplay recording. No claim of test pass counts, visual acceptance or performance improvement is made.

A later implementation should first preserve authoritative modes/endpoints/landings and reuse the existing compiler/sampler/body renderer. The highest-value finite acceptance cases are: one multi-cell Fly route including a support change and real interruption; one shove with rig-specific brace and an intermediate hazard; one controlled/impact transfer landing before actual damage; one raised/rotated window crossing. These are audit reproduction cases, not a new implementation plan.
