## Results that matter first

1. **The corrected source-camera transform was necessary.** Delivered component geometry uses a 45° reconstruction camera and origin `(64,96)`; the display camera is 30° and the unchanged sprite pivot is `(64,87)`. These are different coordinate systems. The new receiver transform preserves the painted quad while interpreting source normals/depth in the source camera. It does not certify the estimated shape as physically accurate.
2. **The remaining black spots are predominantly already present in the float geometry's lighting response.** They are not explained by PNG quantization or unsupported-pixel fallback in the tested components. Exact source-normal discontinuities and provenance are recorded below. Native ambient can make those surfaces readable without modifying the supplied fields.
3. **A concrete negative-elevation ordering gap remains.** The live path makes height-zero floor artwork a universal background, even when an actor is below that floor. The existing flat Crypt/Gallery tests do not establish this case.
4. **Current disclosed item lights are custom shader emitters, not `OmniLight3D` nodes.** Native ambient is a small compatible change. Replacing direct lighting with native point lights needs an explicit comparison because range semantics, per-mesh light limits and the large floor MultiMesh differ.
5. **The earlier performance improvements are real but bounded.** Four-quarter reuse, incremental owner reuse, asynchronous media preparation and stable static order are implemented and tested. The older large-map profile is not a benchmark of newly added modular geometry, new wall policy or the proposed ambient/native-light change.

## Confirmed remaining behavior and concrete gaps

### P2 — Height-zero floor batching can overdraw the intended below-floor relationship

[play.gd:260](/mnt/c/Users/tommaso/Documents/Dev/NDClientGodot/play.gd:260) batches every non-water height-zero floor by material. [grid_order.gd:11](/mnt/c/Users/tommaso/Documents/Dev/NDClientGodot/grid_order.gd:11) assigns those floors the first background key before all actor keys, regardless of the actor's height. With depth testing disabled, an admitted visible actor on negative support can therefore paint over intervening height-zero floor pixels. For a concrete projection, quarter 0 places the ground contact of actor cell `(0,0)` at height `-1` and floor cell `(1,1)` at height `0` at the same projected `(0,64)`.

The offline batching path already guards against negative map/actor height at [terrain_batches.gd:17](/mnt/c/Users/tommaso/Documents/Dev/NDClientGodot/terrain_batches.gd:17); the live path does not. This is confirmed ordering logic, with a source-derived trigger; no native negative-height reproduction was run in this pass. A narrow native below-floor pixel/picking fixture should precede a correction. Do not change the existing flat-floor sort to an unrelated physics system, and do not describe current flat Crypt/Gallery coverage as arbitrary-Z validation.

### P2 — Every lit fragment still evaluates every disclosed custom emitter

[source_lighting.gdshaderinc:34](/mnt/c/Users/tommaso/Documents/Dev/NDClientGodot/presentation/source_lighting.gdshaderinc:34) loops over the entire source texture and checks horizontal distance inside that loop. Native per-object light culling does not reduce this custom loop. Large lit floor quads and overlapping sprite layers multiply its work. This is confirmed algorithmic cost; no new GPU scaling measurement was made, and this review does not invent a current frame-time attribution.

The next useful measurement is actual source count versus viewport GPU time on the same disclosed scene. If direct lighting moves to native lights, remove the corresponding custom contribution rather than lighting twice. If exact horizontal range bands remain mandatory, any reduced custom source list must preserve them and the source-disclosure boundary.

## Native Godot lighting: what can be reused directly

The current runtime uses native Godot meshes, materials, camera, AnimationPlayer/AnimationTree, worker pool, UI and render viewports. It does **not** use native point lights for the four Crypt emitters: [lighting.gd:102](/mnt/c/Users/tommaso/Documents/Dev/NDClientGodot/presentation/lighting.gd:102) publishes positions/ranges to a data texture, and the spatial shaders add their calculated radiance through `EMISSION`. Authored directional sources do create `DirectionalLight3D` nodes. No directional source is authored in the tested Crypt policy.

**Native ambient is the smallest direct reuse for the latest request.** The spatial shaders already output `ALBEDO`; they are not `unshaded` and do not set `ambient_light_disabled`. A `WorldEnvironment` using color ambient, explicit color/energy and zero sky contribution supplies the requested readability floor. It should not be multiplied into the albedo a second time or mislabeled as another torch. Godot documents the color/energy/sky-contribution controls in [Environment](https://docs.godotengine.org/en/4.7/classes/class_environment.html). The existing backend visibility/actor admission gates must remain unchanged; rendering brightness is not an authority for FOW. Already remembered environment geometry remains a separate existing policy, not newly disclosed state.

**Native point lighting can consume the decoded receiver.** Godot's `LIGHT_VERTEX` is specifically a light-receiving position override that does not move the painted fragment, and `NORMAL` is in view space. The corrected source transform can therefore remain while native lighting replaces custom direct radiance. `ALPHA` also puts these materials in the transparent pipeline; enabling physical shadow casting is not a free consequence of adding lights. See [Godot spatial shaders](https://docs.godotengine.org/en/4.7/tutorials/shaders/shader_reference/spatial_shader.html).

There are three concrete comparison requirements before claiming native point lights are equivalent:

1. **Range semantics:** `OmniLight3D` attenuates with spatial distance. The current adapter uses horizontal circular very-bright/bright/outer bands, including dim as an extension. Elevated emitters therefore do not have identical edge behavior under a direct substitution. Decide the optical approximation explicitly while retaining the backend's visibility and activation decisions.
2. **Per-mesh light limits and bounds:** Compatibility defaults to eight omni lights per mesh, and light assignment uses mesh/light AABB intersection. Source-depth lighting can move the receiving point without changing the quad bounds. Native tests must cover a source near that boundary and more than eight lights affecting the floor draw. These limits are documented in [OmniLight3D](https://docs.godotengine.org/en/4.7/classes/class_omnilight3d.html).
3. **The global floor draw:** the live renderer has one floor MultiMesh per material. A MultiMesh has all-or-none culling rather than per-instance culling. Splitting it spatially is not automatically safe: the earlier 8×8 experiment changed original overlapping floor-skirt pixels and was reverted. See [MultiMesh optimization](https://docs.godotengine.org/en/4.7/tutorials/performance/using_multimesh.html). Preserve actual painter output when evaluating smaller draws. Forward+ offers clustered lights, but switching renderer requires its own existing-art/source-color comparison and is not proven faster by this review; see [Godot light limits](https://docs.godotengine.org/en/4.7/tutorials/3d/lights_and_shadows.html).

A native ambient floor addresses the now-rejected zero-luminance presentation directly. Native omni lights alone still use the same supplied normals, so they do not eliminate the measured source-field discontinuities or automatically provide indirect bounce light.

## Existing optimizations and honest validation boundaries

The current source keeps static painter order, merges the small moving actor set, retains unchanged world owner groups, prepares exact current/next-group assets on a worker, uploads completed images on the scene thread and waits at displayed group boundaries. These are useful features of this specific sprite/data architecture, not reasons to replace Godot's scene lifecycle. The rejected affine wall-mask optimization changed native edge sampling and remains reverted. The rejected spatial floor chunking also remains reverted. Neither is counted as a speedup.

The component CPU/GPU comparison proves that the shader follows its numeric contract. It does not prove that the estimated surface is smooth or visually suitable; the black-pixel investigation demonstrates this distinction.
